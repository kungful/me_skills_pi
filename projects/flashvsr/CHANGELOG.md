## v5（2026-11-01 11:35）`d6895c78-…`

**修「长片/大片 100% 失败，且没有任何报错」。**

根因：`--decode-every auto`（整条解码）会把整条片子做成 float32 常驻内存，再加时间维展开
和输出，594 帧 720×1280 → 2560×1408 需要 ≈60 GB，直接顶满容器 57 GB 上限被**内核 OOM 杀掉**。
SIGKILL 不产生 traceback，日志停在 `● Running inference...`，前端只显示"失败"。

诊断入口（容器里没有 dmesg 权限）：`/sys/fs/cgroup/memory.events`（`oom_kill`）、`memory.peak`。

修法：

- `plan_decode_every()`：按 `帧数×宽×高×3×4×2.5` 估内存，超内存预算 35% 自动 `--decode-every 8`；
- `build_cmd()`：Gradio 版和精简版共用一套命令构造（以前两份逻辑已经漂移）；
- `_oom_hint()` + 自动降级重跑：`rc=-9` → 「进程被内核 OOM 杀掉」，`rc=-11` → 「CUDA 算子崩了」，
  命中时自动「整条 → 分片 8 → 分片 4」重试一次；
- 分片时 2K 不再无谓开 `cache-offload`（阈值 3 MP → 6 MP），2K 走快路径。

实测：594 帧 2K 分片 8 → 505 s，峰值显存 11.9 GB，成功出 20.8 MB 视频，`oom_kill` 不再增长。

## v2（2026-11-01 09:35）`0b8b0a19-…`

用户在浏览器里遇到 `Connection to the server was lost`——Gradio 的 queue 走 SSE 长连接，
而平台反向代理会掐长连接。改法：

1. **后台任务 + 轮询**：提交立刻返回（0.4 s），推理跑在进程内线程里，前端 2 s 轮询；
   所有 HTTP 请求都是瞬时的，没长连接可掐。页面关掉/断网都不影响任务。
2. **取消按钮**：`start_new_session=True` + `killpg(SIGINT)`，显存立刻释放。
3. 新增 `/up` 分片续传上传台（2 MB 一片），因为浏览器整块上传 >20 MB 常失败。
